# 基于状态机与微任务驱动的 AI 软件系统开发架构方案

## 1. 方案背景与总体目标

目前项目已完成 **40% 前期筹备**，沉淀了以下关键资产：

* 项目业务描述（Business Requirements & Logic）

* 项目 UI 风格框架定义（UI/UX Style & Component Design）

* 业务流程定义（Workflow Definitions & Schemas）

### 本阶段核心目标（剩余 60%）

在已有设计的框架下，进入 **AI 驱动的代码与功能实现阶段**。通过合理的系统架构与 Agent 流水线设计，实现以下四大目标：

1. **顺畅且完整的开发任务执行**：防止 AI 产生幻觉或因代码上下文过长而失控。

2. **微观进度实时反馈**：使开发者与业务人员能够直观看到当前 Agent 的具体执行动作。

3. **宏观进度全局掌握**：通过动态看板与任务甘特图，精确掌握总体开发进度。

4. **Agent 闭环持续迭代**：支持业务人员（非 IT 人员）在系统上线后，通过 Agent 继续对功能进行增、删、改迭代。

## 2. 核心架构设计：流水线化代码生成

传统的“一次性投喂大量提示词生成整个系统”存在严重失控风险。必须将后续 60% 的开发拆解为严格按照契约执行的微任务（Micro-tasks）。

### 2.1 上下文锚点与契约机制（Specification-Driven Development）

* **资产转化**：将前期 40% 的业务描述、UI 风格与流程定义转化为结构化的 **DSL（领域特定语言）**、**OpenAPI / JSON Schema** 以及数据库设计规范。

* **双向约束**：所有后续生成后端接口或前端 Vue/React 组件的 Agent，都必须遵守契约文档。契约作为“轨道”，避免大模型偏离既定业务逻辑。

### 2.2 多 Agent 协作流水线（Multi-Agent Pipeline）

划分明确的角色 Agent，各自专注特定任务：

```
+------------------------+      +------------------------+      +------------------------+
|    Architect Agent     | ---> |      Coder Agent       | ---> |   QA / Reviewer Agent  |
|  (架构/微任务拆解专家) |      |     (编码与实现者)     |      |    (审阅与自动化测试)   |
+------------------------+      +------------------------+      +------------------------+

```

1. **Architect Agent（架构/拆解专家）**

   * 读取前 40% 规范文件，拆解出粒度明确的《系统开发微任务矩阵》。

   * 自动维护依赖图谱（如：需先建 DB 结构与鉴权，再生成 Controller 和前端页面）。

2. **Coder Agent（编码实现者）**

   * 每次仅接收一个独立的微任务指令及上下文约束。

   * 按照既定 UI 规范与 API 契约生成高质量模块代码。

3. **QA / Reviewer Agent（审阅与测试者）**

   * 对 Coder Agent 生成的代码实施静态代码检查（Linting）与逻辑校验。

   * 自动生成单元测试（Unit Test），确保代码能够正常编译并跑通测试用例。

## 3. 进度反馈与全景掌握：可视化看板机制

为消除“AI 盲盒开发”带来的焦虑，系统引入三层可视化反馈机制。

### 3.1 微观层：实时终端日志流（WebSocket / SSE）

* **交互模式**：采用 WebSocket 或 SSE 流式传输，向前端实时推送 Agent 的执行细节。

* **日志示例**：

  ```
  [10:15:02] [Agent: Architect] 开始校验《用户管理》模块接口契约 ... OK
  [10:15:05] [Agent: Coder] 生成 AuthController.java 代码 ... 完成 (4.2s)
  [10:15:09] [Agent: QA] 执行 单元测试 AuthControllerTest ... 通过 (2/2)
  
  ```

### 3.2 宏观层：动态任务看板与 Gantt 甘特图

* **状态映射**： Architect Agent 生成的任务矩阵在前端呈现为可视化看板。

* **状态自动推演**：
  

  $$
  \text{任务状态}: \text{待办 (To Do)} \longrightarrow \text{进行中 (In Progress)} \longrightarrow \text{已测试 (Tested)} \longrightarrow \text{已合并 (Done)}
  $$

* **总体进度计算**：根据已完成微任务的具体权重实时刷新总体进度百分比（如：$45\% \rightarrow 68\% \rightarrow 100\%$）。

## 4. 持续迭代机制：面向业务人员的 Agent 演进工作流

为了实现“非 IT 业务人员通过与 Agent 对话完成后续功能的增、删、改”，需建立规范的变更加工流（GitOps）。

```
+--------------------+     +---------------------+     +----------------------+     +---------------------+
| 业务人员自然语言需求 | --> |  变更意图解析 (CR)  | --> | 影响分析与微任务拆解 | --> |  Git 分支隔离与更新 |
+--------------------+     +---------------------+     +----------------------+     +---------------------+

```

### 4.1 变更意图解析器（Change Request Intent Parser）

* 业务人员提交描述（例：“帮我给报表模块增加一个导出 Excel 的按钮”）。

* Agent 将自然语言翻译成结构化的 **变更申请单（Change Request, CR）**，确定需修动的业务流程或 UI 模块。

### 4.2 影响范围分析（Impact Analysis）

* Agent 自动评估更改涉及的文件范围：

  * **前端**：报表组件页面（新增导出按钮及事件绑定）

  * **后端**：新增 `/api/v1/report/export` 接口

  * **权限**：更新菜单/按钮权限数据字典

### 4.3 GitOps 安全隔离与热部署

* **分支隔离**：AI 在独立的开发分支（如 `feature/cr-report-export`）上完成代码变更。

* **自动测试与合并**：QA Agent 验证无误后，提交 Pull Request。用户在界面点击“确认应用”，触发 CI/CD 流水线完成热部署或平滑发布。

## 5. 落地实施路线图

| 阶段 | 核心任务 | 交付物/标志节点 | 
| ----- | ----- | ----- | 
| **Phase 1: 任务结构化与契约转化** | 将前 40% 的业务描述、UI 风格与流程定义转化为 JSON/OpenAPI 契约。由 Architect Agent 生成系统微任务拆解清单。 | 《微任务拆解矩阵 JSON》、动态任务看板初始状态 | 
| **Phase 2: 系统骨架与基础基础设施** | 驱动 AI 生成项目脚手架（基础架构、数据库 DDL、鉴权拦截器、菜单与权限管理模块）。 | 可运行的系统空壳骨架 | 
| **Phase 3: 循环迭代编码与实时反馈** | 启动“Coder -> QA -> 部署”自动循环，在前端实时展示日志流与进度百分比。 | 功能模块逐一完成（达到 100% 进度） | 
| **Phase 4: 变更演练与闭环验证** | 模拟业务需求变更（例：修改某表单字段或新增报表导出），校验 Agent 变更解析与 GitOps 自动热更新能力。 | 具备长期自然语言演进能力的软件平台 |
